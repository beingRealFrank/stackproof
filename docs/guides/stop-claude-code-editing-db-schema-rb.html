Stop Claude Code from editing db/schema.rb

Every Rails app has a db/schema.rb, and every coding agent is tempted to edit it. Add a column, tweak an index, fix a default: the file is right there, and editing it looks like the fastest route. It is the wrong one. This guide explains why, what to do instead, and how to make the rule stick. Examples come from the public lobsters/lobsters repository at commit 28bc8d6.

What the file says about itself

The first lines of Lobsters' db/schema.rb read:

# This file is auto-generated from the current state of the database. Instead
# of editing this file, please use the migrations feature of Active Record to
# incrementally modify your database, and then regenerate this schema definition.

The schema file is output, not input. Rails rewrites it from the live database each time you run migrations, so a manual edit is either overwritten at the next bin/rails db:migrate or, worse, it makes the file disagree with the migrations that produced the database. A fresh checkout that loads the schema (bin/rails db:schema:load) then differs from a database that was migrated step by step.

What to do instead

  1. Generate a migration. bin/rails generate migration AddPinnedAtToStories pinned_at:datetime:index writes a new file under db/migrate/ (Lobsters has 23 files there, the newest 20261110163956_remove_cascade_from_foreign_keys.rb).
  2. Run it. bin/rails db:migrate applies the migration and regenerates db/schema.rb.
  3. Prove it reverses. bin/rails db:rollback undoes the last step; run bin/rails db:migrate again.
  4. Commit both files together: the new migration and the regenerated schema.

The Active Record Migrations guide covers the generator names (AddXToY, RemoveXFromY, CreateZs) and reversible migrations.

Related files an agent should leave alone

  • Committed migrations. A migration that is already in git may have run on other machines. Fix mistakes with a new migration. Check with git ls-files db/migrate/<file>.
  • db/structure.sql, the SQL form of the schema, which apps use instead of schema.rb when they need database-specific features. Same rule.
  • config/master.key and encrypted credentials. Secrets; an agent has no reason to read them.

Commands that destroy data

bin/rails db:drop, db:reset and db:schema:load replace or delete the database. They are fine against a test database (RAILS_ENV=test) and dangerous anywhere else. An agent told to "start fresh" should ask first.

Put the rule in writing, then enforce it

Add one line to your CLAUDE.md: "Never edit db/schema.rb; write a migration and run bin/rails db:migrate." Instructions are advisory, though. Claude Code can run a PreToolUse hook before every edit; a hook that exits with status 2 blocks the call and returns its message to the model. A short script that rejects edits to db/schema.rb, db/structure.sql and tracked files in db/migrate/ turns the rule into a guarantee. The Stackproof Rails kit includes such a guard, plus skills for reversible migrations, test-first features, one-line test runs, N+1 hunting and upgrades.
