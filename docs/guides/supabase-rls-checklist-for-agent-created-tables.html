Supabase RLS checklist for tables an AI agent creates

Row level security (RLS) is what keeps one user's rows away from another in a Supabase app. When a coding agent creates a table, it usually writes the columns and forgets the policies, and a table without RLS in an exposed schema can be read and written by anyone holding your public anon key. This checklist is what to verify on every table an agent adds. The example is from the public makerkit/nextjs-saas-starter-kit-lite repository at commit 9ff430d.

1. Turn RLS on for every new table

Creating a table does not enable RLS. In the MakerKit schema file apps/web/supabase/migrations/20241219010757_schema.sql the accounts table is protected like this:

alter table "public"."accounts"
    enable row level security;

Make this the first statement after every create table in the public schema. The Supabase RLS guide explains what happens to a table without it.

2. Write one policy per operation, scoped to a role

With RLS on and no policies, nobody can read or write. Add a policy for each of select, insert, update and delete that the app needs. MakerKit's read policy:

create policy accounts_read on public.accounts for
    select
    to authenticated using (
        (select auth.uid()) = id
    );

Note three things: the policy names its role (to authenticated), it is specific to one operation, and it compares the row to the signed-in user. The update policy repeats the condition in both using and with check, so a user cannot change a row so that it no longer belongs to them.

3. Wrap auth.uid() in a select

MakerKit writes (select auth.uid()), not bare auth.uid(). Supabase recommends the wrapped form because Postgres can then evaluate it once per query instead of once per row.

4. Reject using (true) on anything that writes

A policy that is always true on insert, update or delete means every signed-in user can write every row. Search for it: grep -rn "using (true)" supabase/migrations. Read-everything policies can be correct for genuinely public data, but they should be a deliberate choice.

5. Keep the service-role key on the server

The service-role key bypasses RLS. It must never appear in a variable that starts with NEXT_PUBLIC_, in a "use client" file, or in anything sent to the browser. Check: grep -rn "SERVICE_ROLE" apps/web --include=*.ts --include=*.tsx.

6. Change the schema with a migration, not by editing an old one

Create it with supabase migration new add_notes_table, which writes a timestamped file under supabase/migrations/, and never edit a migration that is already committed. Test locally with supabase db reset, and push to a hosted project only deliberately; an agent that "cleans up" with supabase db push against production is a bad day.

7. Test the policies

supabase test db runs pgTAP tests in supabase/tests/. Write one test that a second user cannot read the first user's row. See the Supabase testing guide.

8. On the server, ask Supabase who the user is

In Server Actions and Route Handlers use supabase.auth.getUser(), which validates the token with the auth server, rather than getSession(), which only reads the cookie. See the Supabase Next.js server-side auth guide.

Make it enforceable

Add the checklist to CLAUDE.md, and back it with hooks: a guard that blocks edits to committed migrations and commands such as supabase db push run from a coding session.
