A CLAUDE.md for Django projects that matches your repo

Most project instructions for coding agents are copied from a template, and the commands in them often do not exist in your repo. For a Django project the agent then runs the wrong test command, forgets the settings it needs, and guesses at the formatter. This guide writes a CLAUDE.md for a Django project by reading the repository first, using the public healthchecks/healthchecks repository at commit cb5c976 as the example.

Step 1: read the real versions

ls manage.py requirements*.txt
grep -n -i "^django" requirements.txt

Healthchecks' requirements.txt pins Django[argon2]==6.1.3. Write the version you find, not the version you remember. It decides which features are available (for example, built-in Content Security Policy support arrived in Django 6.0).

Step 2: find the test command the project actually runs

Look in the README and in the CI workflow rather than assuming pytest:

grep -n "manage.py" README.md
ls .github/workflows; grep -n "manage.py test" .github/workflows/*.yml

Healthchecks' README says to run ./manage.py test, and its coverage workflow runs coverage run --omit=*/tests/*,*/migrations/* --source=hc manage.py test with a SECRET_KEY environment variable set to a dummy value. Both facts belong in CLAUDE.md: the command, and the environment variable it needs. Django's runner also accepts a dotted path for narrower runs, such as ./manage.py test hc.api.

Step 3: find the formatter and type checker

cat CONTRIBUTING.md | grep -n -i "ruff\|black"
cat mypy.ini; grep -n "mypy" .github/workflows/*.yml

Healthchecks' CONTRIBUTING.md asks contributors to format Python with ruff, and a separate workflow runs mypy --strict hc. So the file lists ruff format and mypy --strict hc, and nothing about black or flake8.

Step 4: record the setup commands

The README gives ./manage.py migrate, ./manage.py createsuperuser and ./manage.py runserver. Dependencies come from requirements.txt plus requirements-dev.txt. Settings read environment variables (for example SECRET_KEY and DEBUG in hc/settings.py), and the repo ships hc/local_settings.py.example for local overrides.

Step 5: write the Never section

This is the part agents need most:

  • Never edit a migration that is already committed; add a new one with ./manage.py makemigrations (see what an agent must never touch).
  • Never read or edit .env files or hc/local_settings.py; never commit secrets.
  • Never run ./manage.py flush or migrate <app> zero, and never run against production settings.

The result

## Project facts
- Django 6.1.3 (requirements.txt); settings in hc/settings.py, env-driven.
- Tests: Django runner. Formatter: ruff. Types: mypy --strict.

## Commands
- Setup: pip install -r requirements.txt -r requirements-dev.txt
- Migrate: ./manage.py migrate
- Run: ./manage.py runserver
- Test all: SECRET_KEY=dummy ./manage.py test
- Test one app: SECRET_KEY=dummy ./manage.py test hc.api
- Format: ruff format .   Types: mypy --strict hc

## Never
- Never edit committed migrations; add one with ./manage.py makemigrations.
- Never touch .env files or hc/local_settings.py; never commit secrets.
- Never run ./manage.py flush or migrate <app> zero.

Every line has a source you can point to. Delete any line you cannot source; a shorter file made of true statements beats a long one the agent has to second-guess. If a CLAUDE.md or AGENTS.md already exists, add a marked section instead of rewriting it. And read a project's contribution policy before sending it anything: Healthchecks' CONTRIBUTING.md has a policy about AI-assisted pull requests that you should respect.
