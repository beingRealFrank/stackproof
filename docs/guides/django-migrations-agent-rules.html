Django migrations: what a coding agent must never touch

A coding agent that edits Django models is usually fine. A coding agent that edits migrations can break every other copy of your database. This guide lists the migration files and commands an agent should never touch, why, and what to do instead. The examples come from the public healthchecks/healthchecks repository at commit cb5c976, which has 124 files in hc/api/migrations/ (the newest is 0123_alter_channel_kind.py).

1. Never edit a migration that is already committed

A migration is a record of something that has already run on other databases: your teammates' laptops, staging, production. Django stores which migrations have been applied in the django_migrations table and never reruns an applied one. If an agent "fixes" 0123_alter_channel_kind.py in place, databases that already applied it keep the old schema, while new databases get the edited one. The two drift apart and nothing warns you.

Check whether a file is committed before changing it:

git ls-files hc/api/migrations/0123_alter_channel_kind.py

If that prints the path, the file is tracked: leave it alone and add a new migration instead. A migration you generated a minute ago and have not committed can be deleted and regenerated freely.

2. Never write migrations by hand when makemigrations can

Change the model, then let Django write the file:

./manage.py makemigrations api -n check_muted_until

Read the generated file. Then prove nothing is missing; this command exits with a non-zero status when model changes have no migration:

./manage.py makemigrations --check --dry-run

The migrations documentation describes both flags.

3. Never add a one-way RunPython

A data migration with migrations.RunPython(func) and no second argument cannot be reversed: migrate to an earlier number raises an error. Healthchecks shows both styles. hc/api/migrations/0044_auto_20181120_2004.py uses migrations.RunPython(combine_channel_names) with no reverse, while 0048_auto_20190102_0737.py uses migrations.RunPython(remove_anon_checks, migrations.RunPython.noop). The second form says "undoing this is a no-op", which is explicit and keeps the migration reversible. Always give RunPython a reverse function or RunPython.noop. RunSQL likewise needs reverse_sql. See the migration operations reference.

4. Never import your real models inside a migration

Inside a data migration, get the historical model with apps.get_model("app", "Model"). Importing the live model class ties an old migration to today's code: when the model later loses a field, the old migration breaks for anyone building a database from scratch.

5. Never mix schema changes and data changes in one migration

Put a column addition in one migration and the backfill in the next. On databases that run migrations in a transaction, mixing them can fail or hold locks longer than necessary. For a new required column on a large table, add it nullable, backfill in a separate data migration, then tighten it in a third.

6. Never run commands that destroy data

Three commands an agent should not run on its own, and what to use instead:

  • ./manage.py flush deletes every row in the database. For a clean slate in development, ask the person who owns the database.
  • ./manage.py migrate <app> zero unapplies every migration of an app, which can drop its tables. To undo one change, migrate to the previous number, for example ./manage.py migrate api 0122, and then rerun ./manage.py migrate.
  • Any SQL containing DROP DATABASE, DROP TABLE or DROP SCHEMA.

Tests are safe: Django's test runner creates its own throwaway database. The Healthchecks README runs them with ./manage.py test.

7. Never touch files that hold secrets or local state

An agent does not need .env files, a machine-local local_settings.py, or a local db.sqlite3 to do its job. Healthchecks ships hc/local_settings.py.example for exactly this reason: the real file is yours. Treat generated or third-party directories (staticfiles/, virtualenvs, node_modules/) the same way.

A safe loop for any model change

git ls-files <app>/migrations | tail -3   # see what is committed
./manage.py makemigrations <app>          # generate, then read the file
./manage.py makemigrations --check --dry-run
./manage.py migrate
./manage.py migrate <app> <previous_number>   # prove it reverses
./manage.py migrate
./manage.py test <app>

Make the rules enforceable

Writing these rules in CLAUDE.md helps, but a hook is stronger: Claude Code runs a PreToolUse hook before every tool call, and a hook that exits with status 2 blocks the call and sends its message back to the model. A small script can refuse edits to tracked files under */migrations/, and refuse shell commands that match flush, migrate <app> zero or DROP. The Stackproof Django kit ships such a guard, plus skills for migrations, model changes, tests, query performance and deployment checks.
